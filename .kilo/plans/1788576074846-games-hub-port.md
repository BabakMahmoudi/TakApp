# Plan: Port CafeBazi's 3 games (Spin / Tap / Clock) to TakApp

## Goal

Recreate CafeBazi's three server-settled games — **Spin the Wheel** (`spin`), **Tap the Bean** (`tap`), **Stop the Clock** (`clock`) — in TakApp, paying a **1 TAK prize** from a server-held house account on a win. Adapted to TakApp's **non-custodial** model and Cloudflare Workers + D1 stack.

## Resolved decisions

1. **Prize payout mechanism**: a second **server-held Stellar key** (`GAME_ACCOUNT_SECRET`, env-only) — the "casino"/house account — exactly like `FUNDING_SECRET`. The server signs `casino → winner` TAK payouts only. Users keep full custody of their own funds.
2. **Paid plays**: **out of scope for v1** — free plays only (3/day default). The 1-TAK `paidPlayFee` field is kept in the settings schema/UI for a later phase but no fee flow is built. No client-signed fee step.

## Architecture deltas vs CafeBazi (non-custodial adaptation)

| CafeBazi | TakApp port |
|---|---|
| Custodial; server signs fee + payout | Non-custodial; server signs **only** casino→winner payout (and admin casino withdraw) |
| `game_accounts` table (encrypted secret) | `GAME_ACCOUNT_SECRET` env var; pubkey derived via `Keypair.fromSecret` |
| `transactions` ledger + `balances` cache | No such tables; payouts recorded in `game_plays` + (optional) `payments` |
| `bigint` + `takToNumeric` money | **stroop strings** + `addStroops`/`compareStroops`/`lumensFromStroops` (`packages/shared/src/money.ts`) |
| Postgres `jsonb` | D1 SQLite; settings/params/performance stored as **JSON text** |
| `next-intl` `t(key, {count})` | Flat `useI18n().t(key)` (no interpolation) — dynamic text composed with `formatAmount`/`formatAmountLatin` |
| Vercel cron / Node | Cloudflare Worker; `Intl.DateTimeFormat` timezone (supported) for Iran day boundary |

## New server-held key (casino) — security contract

- New env secret `GAME_ACCOUNT_SECRET` (Stellar S-key). **Never** in `[vars]`, `wrangler.toml`, D1, or client bundles. Deploy via `wrangler secret put GAME_ACCOUNT_SECRET`; add to `.dev.vars` locally; placeholder line in `.dev.vars.example`.
- Add `GAME_ACCOUNT_SECRET: string` to `WorkerEnv` (`apps/web/src/server/trpc/env.ts`).
- Bounded purpose (mirrors `FUNDING_SECRET`): the casino key signs **only** (a) `casino → winner` game payouts and (b) `casino → dest` admin withdraws. It never signs user transactions, never issues/moves TAK, never touches user balances.
- **Document the exception**: AGENTS.md currently says the server holds *exactly one* Stellar key. Update AGENTS.md + ARCHITECTURE.md to describe the bounded second key.

## Data model (D1 — `packages/shared/src/db/schema.ts`)

Add two tables (Drizzle `sqliteTable`, camelCase props → snake_case columns, money as stroop strings):

```ts
export const gameSettings = sqliteTable('game_settings', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  gameKey: text('game_key').notNull().unique(),
  settings: text('settings').notNull(),                 // JSON string (TAK amounts as stroop strings)
  updatedByUserId: integer('updated_by_user_id').references(() => users.id),
  updatedAt: integer('updated_at', { mode: 'timestamp_ms' }).notNull(),
});

export const gamePlays = sqliteTable('game_plays', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  gameKey: text('game_key').notNull(),
  userId: integer('user_id').notNull().references(() => users.id),
  playType: text('play_type').notNull().default('free'),// 'free' only in v1
  status: text('status').notNull(),                     // pending|won|lost|abandoned|payout_failed
  params: text('params').notNull(),                     // JSON string
  performance: text('performance'),                     // JSON string, nullable
  score: integer('score'),
  prize: text('prize'),                                 // stroop string, nullable
  payoutTxHash: text('payout_tx_hash'),
  startedAt: integer('started_at', { mode: 'timestamp_ms' }).notNull(),
  settledAt: integer('settled_at', { mode: 'timestamp_ms' }),
  createdAt: integer('created_at', { mode: 'timestamp_ms' }).notNull(),
}, (t) => ({
  userGameCreatedIdx: index('idx_game_plays_user_game_created').on(t.userId, t.gameKey, t.createdAt),
  gameCreatedIdx: index('idx_game_plays_game_created').on(t.gameKey, t.createdAt),
  statusIdx: index('idx_game_plays_status').on(t.status),
}));
```

No `game_accounts` table (env-only casino). Generate + apply migration: `pnpm db:generate` then `pnpm db:migrate`.

## Server-side TAK transfer helper (new)

Add `apps/web/src/server/stellar/tak-transfer.ts` with a function that builds + signs + submits a SEP-41 `transfer` from a server-held key (casino), mirroring the client Web Worker `submit-payment` path but server-side:

- Use `@stellar/stellar-sdk/no-axios` (`Address`, `Contract`, `Keypair`, `nativeToScVal`, `TransactionBuilder`) and `@stellar/stellar-sdk/no-axios/rpc` (`Server as SorobanRpc`, `assembleTransaction`, `Api as SorobanApi`), consistent with `funding.ts`/`horizon.ts`.
- Flow: `loadAccount(source)` → `Contract(TAK_CONTRACT_ID).call('transfer', fromScVal, toScVal, i128 amount)` → `TransactionBuilder(...).setTimeout(0)` → `simulateTransaction` → `assembleTransaction(...).build()` → sign → submit XDR to Horizon (`submitTransactionToHorizon` from `funding.ts`).
- Return `{ txHash, envelopeXdr }`.
- **Risk to verify at implementation**: confirm the `no-axios` rpc entry exports `assembleTransaction` + `Api.isSimulationError` (the client uses the non-`no-axios` `@stellar/stellar-sdk/rpc`). If the no-axios entry lacks them, import from the bundled `@stellar/stellar-sdk` rpc entry (server bundle is fine as long as it's Workers-compatible, as the SDK already is).

## Games service (`apps/web/src/server/games/service.ts` — `server-only`)

Port `CafeBazi/src/services/games.ts`, adapted:

- `GameError` with the same code set (`INVALID_GAME`, `GAME_DISABLED`, `GAME_ACCOUNT_NOT_READY`, `GAME_OUT_OF_FUNDS`, `GAME_IN_PROGRESS`, `PLAY_NOT_FOUND`, `PLAY_EXPIRED`, `PLAY_NOT_PENDING`, `INVALID_PERFORMANCE`, `DAILY_PLAY_LIMIT`, `PAYOUT_FAILED`, `INTERNAL`).
- Per-game Zod settings schemas (money fields as stroop-string regex `^\d+$`; `prizeTak` ≥ `stroopsFromLumens('1')`).
- `playDayStart()` — Iran day via `Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Tehran', ... })` (same as CafeBazi).
- `getSettings(gameKey)` → stored row (Zod-parse the JSON text) or `defaultSettings`.
- `createParams(gameKey, settings)` — `spin` outcome pre-decided with `crypto` RNG; `tap`/`clock` duration/target + `startedAtMs`.
- `isValidPerformance(...)` — bounded client input: spin `{ack:true}`; tap `taps ≤ 3×targetTaps`; clock `elapsedMs ≤ completionWindowSeconds*1000`.
- `getCasinoPublicKey()` + `getCasinoTakBalance()` — derive pubkey from `GAME_ACCOUNT_SECRET`; balance via a new `fetchTakBalance` (reuse `fetchBalances` in `horizon.ts` or add a narrow helper).
- `startGame({userId, gameKey})` (free-only):
  1. Validate game + `enabled`; casino pubkey derivable (`GAME_ACCOUNT_NOT_READY`), casino TAK balance ≥ `prizeTak` (`GAME_OUT_OF_FUNDS`).
  2. Lazily abandon any expired pending play for the user+game.
  3. Count settled free plays today (Iran day); if ≥ `freePlaysPerDay` → `DAILY_PLAY_LIMIT` (paid path stubbed out in v1).
  4. Insert `pending` `game_plays` row with rolled `params`, `prize`, `startedAt`.
  5. Return `{ playId, gameKey, playType:'free', params, freePlaysRemaining }`.
- `finishGame({userId, playId, performance})`:
  1. Load play; `PLAY_NOT_FOUND` if missing; if already settled → return stored result (idempotent).
  2. If expired → mark `abandoned`, return.
  3. Validate performance (`INVALID_PERFORMANCE`); settle via `settle()`.
  4. `lost` → update row, return.
  5. `won` → check casino TAK ≥ prize; build+sign+submit `casino→winner` TAK transfer; on success set `status='won'` + `payoutTxHash`; on failure set `payout_failed` + throw `PAYOUT_FAILED`. Optionally insert a `payments` row (see below).
- `getGameHistory(userId, limit=20)`.
- `listGames(userId)` → enabled games + settings + `freePlaysUsed/Remaining` (no paid counts in v1).
- `updateSettingsForAdmin`, `listGamesForAdmin`, `recentPlaysForAdmin`, `retryPayoutForAdmin` — port from CafeBazi; admin variants write `admin_audit_log` via `logAdminAction` (TakApp's existing helper).

### Recording payouts (integration)

- Always record payout in `game_plays.payoutTxHash` + `status`.
- **Recommended (optional but cheap)**: also insert a `payments` row (`userId = winner`, `recipientPublicKey = winner pubkey`, `amount = prize`, `asset:'TAK'`, `txHash = payoutHash`, `status:'submitted'`) so wins surface in the Telegram bot's `history` intent (which reads `payments`). Do this directly in the service (not via `payments.record`, whose validation doesn't apply). Mark as a small follow-up if desired to keep v1 diff minimal.

## Security & failure modes

- Casino key env-only; never logged, never in D1/bundle. Payout amount always `settings.prizeTak` (validated ≥ 1 TAK).
- Client-reported performance is bounded (tap `3×target`, clock `≤ window`); spin outcome is server pre-decided.
- Free daily quota counts **settled** plays only (no farming); Iran day boundary; paid plays never consume free quota (n/a in v1).
- Idempotency: settled plays return stored result on repeated `finish`; payout submit failure → `payout_failed` (admin-retryable, fresh txHash — never reuse a failed envelope); `GAME_ACCOUNT_NOT_READY`/`GAME_OUT_OF_FUNDS` surface at `start`/`finish`.
- Corrupt `game_settings` JSON → fall back to defaults (Zod parse fails defensively).
- PWA/offline: games are server-settled (network required) — not part of the offline core flow; service-worker caching unchanged.
