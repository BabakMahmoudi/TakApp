# Migrate TAK from classic asset to SEP-41 (Soroban) token

## Goal

TAK is a **custom SEP-41 Soroban token** (contract `CBI3WR5NQZUQ5PAPV4TBCOFMJ3MOJVZVMH5CKCGVOP63YV2SPFZN3Z7C`, 7 decimals, testnet), not a classic Stellar asset. Today the codebase treats it as a classic `credit_alphanum4` asset, so its balance is never fetched, the signup trustline targets a non-existent asset, and payments/issuance use `Operation.payment`.

Migrate **all four flows** to SEP-41: balance read, signup, payments, and gift issuance (gift becomes **no server issuance** — removed).

## Key decisions (confirmed)

- **Token**: custom SEP-41 contract, ID `CBI3WR5NQZUQ5PAPV4TBCOFMJ3MOJVZVMH5CKCGVOP63YV2SPFZN3Z7C`.
- **Decimals**: 7, matching the app's stroop model (`1 TAK = 10^7` raw units = `10^7` stroops). Raw integer balance maps 1:1 to stroop strings. Keep a small scaling helper anyway so the assumption is explicit.
- **RPC**: `https://soroban-testnet.stellar.org` (testnet), read from env as `SOROBAN_RPC_URL`.
- **Gift**: no server-side mint/transfer. Remove `wallet.claimGift` and the funding-account TAK issuance path. Funding account keeps only `createAccount` (XLM).
- **Balance read approach**: simulate the SEP-41 `balance(Address)` function via Soroban RPC and decode the returned `i128` with `scValToNative` (returns `bigint`). Reuse the Horizon account already loaded for XLM as the simulation source. (`getContractData` on the standard `Balance` storage key is a lower-latency alternative if simulation proves noisy; not required.)

## SDK facts (verified against installed `@stellar/stellar-sdk@15.1.0`)

- Server (Cloudflare Worker) must use `no-axios` entrypoints:
  - `import { Contract, Address, scValToNative } from '@stellar/stellar-sdk/no-axios';`
  - `import { Server as SorobanRpc, Api as SorobanApi } from '@stellar/stellar-sdk/no-axios/rpc';`
- Client Web Worker currently imports the full axios SDK (`apps/web/src/workers/stellar-worker.ts:4`); keep that convention:
  - `import { Contract, Address, nativeToScVal } from '@stellar/stellar-sdk';`
  - `import { Server as SorobanRpc, Api as SorobanApi, assembleTransaction } from '@stellar/stellar-sdk/rpc';`
- `Contract.call(method, ...scVals)` returns an `xdr.Operation<InvokeHostFunction>`.
- `rpc.Server.simulateTransaction(tx)` returns `Api.SimulateTransactionResponse`; guard with `Api.isSimulationError(sim)`.
- `assembleTransaction(raw, sim).build()` returns a signable `Transaction`.
- `scValToNative` maps `i128` → `bigint` (verified in `stellar-base` sources).

## Out of scope / assumptions

- The TAK contract is already deployed and usable on testnet (ID provided). Deploying/initializing it is not part of this change.
- No migration of existing D1 data: the `gifts` table stays in `packages/shared/src/db/schema.ts` but is left unused (no destructive D1 migration). Verification still exists but no longer gates a gift.
- `payments.record` and the `payments` schema are unchanged (asset `TAK`, stroop amounts, tx-hash idempotency still apply).

## Validation

- `pnpm typecheck`, `pnpm lint`, `pnpm test` from the repo root.
- Manual smoke on testnet: create a wallet (should skip the trustline step and land on login), view balance (XLM + TAK), send TAK to another account, and confirm `/tak` no longer offers a claim.

## Risks

- Soroban transaction resource fees: signup funds 5 XLM (unchanged), which should cover a `transfer`; monitor for `tx_insufficient_fee`/resource errors on the first manual transfer.
- Balance read depends on RPC availability; an RPC outage now fails the balance query (same visibility model as Horizon failures today).
- `simulateTransaction` for reads requires the source account to exist; signup already funds the account before login, so this holds in the normal flow.
